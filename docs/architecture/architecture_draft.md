Файл с объяснением выбора архитектурных решений

Почему Playwright
- Avito API требует бизнес-аккаунт
- API сейчас недоступен
- нужен быстрый MVP
- browser automation позволяет начать разработку немедленно
- архитектура проектируется с возможностью перехода на API

Почему PostgreSQL
- разработчик уже немного знаком с PostgreSQL
- PostgreSQL хорошо работает с Docker
- подходит для роста проекта
- поддерживает конкурентную работу лучше SQLite
- позже можно использовать pgvector

Почему локальные LLM
- минимальный бюджет
- есть собственное железо
- нужен оффлайн-запуск
- отсутствие расходов на API

Главный архитектурный принцип

Browser automation должен быть только транспортным слоем.

Playwright отвечает только за:
- получение сообщений
- отправку сообщений
- получение информации о чатах

Вся бизнес-логика должна быть независимой от Playwright.

Это необходимо для:
- будущего перехода на Avito API
- возможного подключения Telegram
- упрощения поддержки проекта

Роль AI в системе

LLM не должна:
- хранить знания
- придумывать цены
- быть источником данных

LLM используется только для:
- генерации текста
- уточняющих вопросов
- естественного общения
- форматирования ответа

Все данные должны храниться отдельно:
- FAQ
- цены
- примеры работ
- шаблоны

План хранения данных

Планируется хранение:
- FAQ
- прайсов
- примеров работ
- prompt templates

в отдельных файлах и/или PostgreSQL.

Ограничения MVP

На первом этапе:
- нет Avito API
- нет distributed architecture
- нет сложной очереди сообщений
- нет CRM
- нет vision AI

Главная цель MVP:
- стабильное получение сообщений
- автоответы
- базовая AI-логика
- сохранение диалогов

План дальнейшего развития

После появления доступа к Avito API:
- Playwright Adapter должен быть заменён на API Adapter
- остальная архитектура не должна требовать серьёзных изменений
